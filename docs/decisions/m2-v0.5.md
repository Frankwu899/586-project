# M2 input drafts and v0.5 contracts

The M2 handoff authorizes task-local partial inputs and explicit Apply. At implementation start the prepared branch `feat/workspace/m2-brief-experience` at `0c54231` contained prerequisite PR #3 head `da95ad3`, still draft/open/unmerged. The prepared handoff commit is retained; the implementation is stacked on `feat/video-analysis/bilingual-provider-contracts`.

## Ownership and integration

Shared-file coordination: the contract editor owns `models.py`, storage/migration and schema/type generation; the integrator owns `service.py`, `api.py`, `adapters.py`, sample data and workspace integration; assistance owns its separate provider/models/configuration; frontend owns the input editor and styling; browser and integration test editors own their suites. Contracts and storage precede consumers; regeneration follows canonical changes. All changes are reviewed together before publication. No independent schema fork or provider approval path is introduced.

## Independent editor channel

`m2_drafts` lives in the existing SQLite database beside task aggregates. Its optimistic `draft_version` is independent of `task.version`. Partial fields, stable claim rows and raw source notes persist without creating a formal brief, invalidating output or rejecting an active reference job. The client serializes/coalesces saves, keeps newer local text while an older save finishes, and flushes before Apply or creative actions. A version conflict preserves local text and requires an explicit reload decision.

The checkpoint hashes the structured fields and all claim rows, including excluded claims. Notes and unaccepted proposals do not create pending formal changes. Apply checkpoints the reviewed excluded rows so a retained unconfirmed alternative does not permanently block the task. Subsequent edits require review again.

## Formal inputs and transactions

`BrandTaskBrief` remains strict. `selling_points` is the exact ordered statement projection of `claim_details`; every detail has a stable claim ID, statement, optional support/URLs/qualification and confirmation origin. Newly applied input contains only confirmed claims. User permission is not verification, and the UI says so. Updating statement or qualification clears permission on both client and server. URLs are validated as HTTP(S) references and never fetched.

Apply uses one immediate SQLite transaction: check task version, draft version and applied reference; validate all required inputs; build the complete provider payload; compare every field including optional restrictions and claim metadata; append/invalidate only on meaningful change; then save the checkpoint. Identical Apply does not increment task version or formal revision or clear approval. Exact retries are idempotent. Failed validation or storage rolls back both task and draft. The old `/brief` route requires explicit confirmed metadata and follows equivalent Apply semantics; it cannot replace pending independently edited input.

Creative generation, refinement, direction approval and production generation check the persisted M2 gate inside the same transaction as admission. Completion of an already admitted job does not recheck a later draft edit. A meaningful Apply still changes the task version, so the existing stale-result guard rejects a superseded response. Reference upload, processing and review remain independent.

## Migration

The prerequisite uses literal `0.4.0` versions and forbids extra fields. Version `0.5.0` therefore records the new applied claim metadata and separate draft/proposal contracts. Historical schemas and examples remain unchanged. Current schemas and TypeScript are generated from canonical Pydantic models.

Migration validates the retained historical schema and archives the exact original payload and hash transactionally. Applied wording, IDs/revisions, original analysis, corrections, evidence, frame clocks, reviews, approvals and outputs remain intact. Migrated claims receive deterministic IDs and `legacy_unrecorded`, never invented user confirmation. A separate review requirement blocks new creative actions. Explicit confirmation and changed Apply create the next revision and invoke normal invalidation. Migration alone preserves existing approval/currentness. Earlier migrations retain their timing behavior and lead to the current contract.

## Assistance boundary

M2 assistance has its own bounded request/response protocol and does not extend `ProcessingJob.operation`. Extraction uses only saved notes and requires exact source excerpts. Audience/goal suggestions are labeled and require acceptance. Provider content cannot propose IDs or approvals, confirm claims, or change task state. Selected/edited candidates are adopted in a single version-checked draft transaction; a stale batch is rejected. Manual editing works with no provider. Deterministic assistance is injected only through offline test fixtures; configuration cannot silently substitute it for a failed real response.

M7 remains the generated production creative brief and storyboard. No brand library, cross-task profile, web research, additional output schema or change to reference-frame/storyboard-second semantics is included.
