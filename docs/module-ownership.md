# Module ownership and source map

The module names below are branch scopes for the current repository. Every branch contains all modules. Most modules share some files; the name does not grant exclusive ownership or require a directory reorganization. Read [branch workflow](branch-workflow.md), [architecture](architecture.md), and [interfaces](interfaces.md) alongside this map.

The v0.4 provider foundation is implemented; see [the current handoff](handoff/bilingual-provider-contracts.md). Andrea owns permitted bilingual evaluation and recognition-quality follow-ups. Frank owns workflow/creative-quality review and integration. Other module changes need an explicitly assigned task owner; the map does not invent additional assignments. Team members can maintain reference examples and annotations with the integrator's review. GitHub usernames and automatic CODEOWNERS assignments are not assumed.

## Coordinate the four shared backend files

| Shared file | Why concurrent changes need coordination |
|---|---|
| `backend/app/models.py` | One authoritative contract serves every module. Field, enum, invariant, or timing changes affect saved data, generated schemas/types, fixtures, and consumers. |
| `backend/app/adapters.py` | Recognition and creative protocols currently share this file with sample implementations. Both provider owners may need it; agree on the exact interface and wiring edits first. |
| `backend/app/service.py` | Shared persistence orchestration, jobs, revision checks, confirmation, approval, invalidation and exports. A provider change must not bypass these gates. |
| `backend/app/api.py` | Shared HTTP request/response shapes and application setup. A route/config change can affect both frontend and backend tests. |

Before parallel work, record the planned shared-file edits, interface changes, responsible editor, and merge order in the tasks/PRs. Andrea and Frank should agree on changes that touch both provider boundaries. For competing edits, finish and merge the shared contract/wiring change first, then update dependent task branches from `main` using a normal merge. Do not rely on another agent's uncommitted state or silently resolve contradictory product decisions.

Keep provider transport, request building, response parsing and vendor errors in separate implementation files where practical. For example, a future `backend/app/providers/` package could hold recognition and creative implementations; this package now contains the v0.4 capability, transport, recognition and creative implementations. Make only the small, agreed protocol/wiring edits in shared files. Adapters return validated domain objects; the service retains responsibility for task persistence, job status, and user approval. Keep credentials on the backend and never convert provider failures into successful sample results.

For a shared contract change, update `backend/app/models.py`, interface documentation, semantic validation, fixtures/migrations and consumers together. Regenerate rather than hand-edit generated artifacts:

```bash
.venv/bin/python scripts/export_contracts.py
npm --prefix frontend run contracts:generate
.venv/bin/python scripts/export_contracts.py --check
npm --prefix frontend run contracts:check
```

Preserve historical v0.1/v0.2/v0.3 schemas and fixtures. Reference observations/sections retain zero-based integer `start_frame` and exclusive `end_frame`; actual probed boundaries supply timing, with no invented missing FPS. Storyboard planning remains in seconds. Preserve original analysis, corrections, source provenance, migration archives, saved feedback, exact revisions, and explicit review/approval gates.
